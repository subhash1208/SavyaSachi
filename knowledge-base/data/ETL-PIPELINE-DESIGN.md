# VaidyaVaani — KB Ingestion ETL Pipeline Design
**Status:** In Progress  
**Last Updated:** March 3, 2026  
**Owner:** Ingestion Team

---

## Overview

This document describes the ETL pipeline for ingesting clinical documents into the VaidyaVaani Bedrock Knowledge Base (General Triage KB — Layer 2/5). The pipeline is intentionally simple: upload files, generate metadata sidecars, sync to KB. The chunk tagger handles all per-chunk precision tagging during sync.

**This pipeline is ONLY for the General Triage KB.** Emergency scripts (Layer 1) are handwritten JSON in DynamoDB — never automated.

---

## Pipeline Architecture

```
.md or .pdf files uploaded to S3: kb-ready/
    → Step 1: S3 event triggers Metadata Lambda
        → generates .metadata.json sidecar (document-level tags)
        → writes ingestion registry entry to DynamoDB
    → Step 2: KB Sync (manual or scheduled)
        → FM-as-parser handles PDFs (including flowcharts → text)
        → Semantic chunking (512 tokens, threshold 85)
        → Chunk Tagger Lambda adds per-chunk tags
            (patient_category, age_group, topic, condition, urgency, pregnancy_flag)
        → Chunk-level tags overwrite document-level tags on collision
        → OpenSearch Serverless stores vectors + metadata
```

**2 Lambdas. 3 steps. That's it.**

## S3 Bucket Structure

```
vaidyavaani--kb-data/
└── kb-ready/
    ├── diabetes_mellitus_type_2.md
    ├── diabetes_mellitus_type_2.md.metadata.json
    ├── vol1_eng_non_emergency.md
    ├── vol1_eng_non_emergency.md.metadata.json
    ├── icmr_stw_headache.pdf
    ├── icmr_stw_headache.pdf.metadata.json
    └── ...
```

**Rules:**
- All files (`.md` and `.pdf`) go directly into `kb-ready/`
- Each file must have a `.metadata.json` sidecar (auto-generated by Metadata Lambda)
- PDFs are parsed by the FM-as-parser during KB sync — no pre-processing needed
- `.md` files are parsed by the default parser during KB sync
- No subfolders, no splitting, no intermediate prefixes

## Step 1 — Metadata Lambda (Auto-triggered)

**Trigger:** S3 ObjectCreated event on `kb-ready/*.md` or `kb-ready/*.pdf`  
**Service:** AWS Lambda (`vaidyavaani-metadata-generator`)  
**Input:** `.md` or `.pdf` file landing in `kb-ready/`  
**Output:**
- `.metadata.json` sidecar written to `kb-ready/`
- Registry entry written to DynamoDB `vaidyavaani-ingestion-registry`

### Document-Level Metadata Schema

These are fields that are consistent across an entire document — they don't vary chunk to chunk.

```json
{
  "metadataAttributes": {
    "source":         "WHO_IMCI | WHO_IMAI | ICMR_STW | RMNCH_A | WHO_SNAKEBITE",
    "condition_type": "chronic | general_triage | general",
    "severity":       "critical | moderate | mild"
  }
}
```

**Note:** `patient_category`, `age_group`, and `pregnancy_flag` are NOT set at document level. These vary within multi-category documents (e.g. WHO Vol 1 covers adult + pediatric + maternal). They are set per-chunk by the Chunk Tagger during KB sync.

### Keyword Rules for Auto-Detection

| Field | Value | Filename Keywords |
|---|---|---|
| condition_type | chronic | diabetes, hypertension, tuberculosis, chronic |
| condition_type | general_triage | imai, imci, non_emergency, vol1_eng |
| condition_type | general | (fallback) |
| source | WHO_IMCI | imci |
| source | WHO_IMAI | imai |
| source | RMNCH_A | rmnch, maternal, antenatal |
| source | WHO_SNAKEBITE | snake, venom |
| source | ICMR_STW | (fallback) |
| severity | critical | cardiac, snakebite, seizure, emergency |
| severity | mild | headache, cold, cough |
| severity | moderate | (fallback) |

### DynamoDB Ingestion Registry Schema

**Table:** `vaidyavaani-ingestion-registry`  
**PK:** `document_id` (MD5 hash of S3 path)

```json
{
  "document_id":    "md5(s3_path)",
  "s3_path":        "s3://vaidyavaani--kb-data/kb-ready/filename.md",
  "filename":       "filename.md",
  "ingested_at":    "2026-03-03T10:30:00Z",
  "condition_type": "chronic",
  "source":         "ICMR_STW"
}
```

This is a simple ingestion log — when was this document uploaded, what source is it from, where is it in S3.

## Step 2 — KB Sync

**Trigger:** Manual (or scheduled EventBridge rule)  
**Service:** Bedrock Knowledge Base sync

### KB Data Source Config

| Setting | Value |
|---|---|
| Parser | Foundation Model as Parser (handles PDFs including flowcharts → text) |
| Chunking | Semantic |
| Max buffer size | 3 |
| Max token size | 512 |
| Breakpoint threshold | 85 |
| Custom Transformation Lambda | `vaidyavaani-kb-chunk-tagger` |

### Why FM-as-Parser

Clinical PDFs contain flowcharts (treatment algorithms, decision trees). The default parser saves these as images and generates brief captions. FM-as-parser reads the flowchart visually and converts it to structured text — preserving decision points, branches, and outcomes. This is critical for ICMR STWs which heavily use algorithm flowcharts.

### Chunk Tagger — Per-Chunk Tags

The custom transformation Lambda runs on every chunk after chunking. It reads the full chunk text and assigns 6 metadata fields based on content keywords:

```json
{
  "patient_category": "pediatric | adult | maternal | geriatric | general",
  "age_group":        "0-5 | 6-12 | adult | geriatric",
  "topic":            "dosage | contraindication | side_effects | emergency_signs | referral | lifestyle | monitoring | counselling | symptoms | diagnosis | prevention | general",
  "condition":        "diabetes | dengue | diarrhea | headache | jaundice | fever | pneumonia | snakebite | cardiac | general",
  "urgency":          "emergency | urgent | routine",
  "pregnancy_flag":   "applicable | not_applicable"
}
```

**Key design decision:** `patient_category`, `age_group`, and `pregnancy_flag` are set at chunk level, not document level. This means a single WHO Vol 1 document (300 pages, adult + pediatric + maternal) gets correct per-chunk tags without needing to be split into separate files. Chunk-level metadata overwrites document-level metadata on collision (per AWS docs).

## KB Query — How Filters Are Used at Runtime

When the app queries the KB, it combines document-level and chunk-level filters:

```python
# Example: pediatric patient asking about diarrhea treatment
filter = {
  "andAll": [
    {"equals": {"key": "patient_category", "value": "pediatric"}},
    {"equals": {"key": "condition",        "value": "diarrhea"}},
    {"equals": {"key": "topic",            "value": "counselling"}}
  ]
}
```

## What Does NOT Go Into the KB

| Content | Where It Goes |
|---|---|
| Emergency ABCDE scripts | DynamoDB `vaidyavaani-emergency-scripts` (Layer 1) — handwritten JSON, never automated |
| ICD-10 codes | Hardcoded in Lambda + DynamoDB (Layer 4) |
| Benchmark datasets | Evaluation pipeline only, never in KB |

**Included in KB:** Drug dosage tables, algorithm flowcharts (converted to text by FM-as-parser), management workflows, counselling text, danger signs. Dosage context is needed for the dual-source merge pattern.
